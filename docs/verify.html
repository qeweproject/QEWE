VERIFY BEFORE YOU RUN

Check your copy.

Integrity, provenance and code review answer different questions.

Experimental preview. No independent audit.
Never enter a Ledger phrase into any computer application. Use public addresses or a disposable test wallet first.

1. Start at the official release

Use qeweproject/QEWE Releases. Do not trust search ads, mirrors or unsolicited support messages. The website has no wallet-connection or recovery-phrase form.

2. Compare SHA256

Download SHA256SUMS.txt with the installer. Compare every character against the local file, using PowerShell on Windows:

Get-FileHash .\QEWE_3.2.0-rc.3_Windows_x64_Setup.exe -Algorithm SHA256

Ubuntu/Linux:

sha256sum QEWE_3.2.0-rc.3_Ubuntu_amd64.deb

Mac Apple Silicon (use x64 instead for Intel):

shasum -a 256 QEWE_3.2.0-rc.3_macOS_arm64.dmg

A hash checks consistency with that manifest. An attacker who can replace both can change both.

3. Verify build provenance

With a current official GitHub CLI, substitute your actual filename:

gh attestation verify ./QEWE_3.2.0-rc.3_Windows_x64_Setup.exe   --repo qeweproject/QEWE   --signer-workflow qeweproject/QEWE/.github/workflows/release.yml   --deny-self-hosted-runners

Inspect the source commit, tag and workflow reported. A Sigstore bundle is attached for verification with --bundle. Authentication or trust-root network access may be needed. An attestation identifies the build; it does not certify safe code or protect you from a compromised maintainer/dependency.

4. Read or build the exact source

git clone https://github.com/qeweproject/QEWE.git
cd QEWE
git checkout v3.2.0-rc.3
npm ci --ignore-scripts
npm audit --audit-level=low
npm audit signatures
npm run build:vendor
npm run verify:vendor
npm test
npm run test:dom

Use Node.js 24 and follow the complete verification guide. The installed-payload checker compares application bytes, icons and runtime controls to source. Independent bit-for-bit installer reproducibility has not been established. The SBOM contains development and runtime dependencies, not only shipped code.

5. Understand the boundary

The intended renderer/worker design has local scripts, sandboxing, context isolation and a CSP with network connections blocked. Main-process RPC calls validate public inputs and new destinations require native consent. Optional metadata services begin off.

This is not a formal proof of isolation: a compromised renderer could encode a secret into apparently valid public requests. The OS, executable and dependencies also matter. For software-key signing use a trusted computer physically disconnected from networking, in addition to the application's offline mode. RPCs can correlate addresses and lie. Signed exports authorize their exact transaction.

Signatures and real-device tests

Windows is not Authenticode-signed. Mac builds are ad-hoc signed and not Apple-notarized. Do not disable system-wide security to bypass a warning. Physical Ledger/Trezor/BitBox02 and a complete target-OS execution matrix have not been tested by the build environment. Read SECURITY.md.
